# Working on Luna

Notes for anyone — person or agent — making changes here. Everything below is a
rule the codebase already keeps; breaking one is a regression, not a variation.

## Buttons answer

**Every button Luna draws responds to a hover *and* to a press.** If you add a
control the pointer aims at, it is not finished until it does both.

- **Hover** — `Tokens.Surface.hover` (6 %) over whatever the control is made of,
  cross-faded on `Tokens.Motion.controlHover`. Use `Tokens.Motion.wash(_:to:)`,
  which handles Reduce Motion and the `CATransaction` timing for you.
- **Press** — `Tokens.Surface.selected` (12 %, the same wash at twice the lift)
  **plus** `Tokens.Motion.swell(_, to: Tokens.Motion.pressSwell)` on the way
  down and `to: 1` on the way up.
- **A control with no material of its own hands the press up.** Half a capsule
  swelling inside the other half is not a press, so an item inside a capsule
  exposes an `onPressChange` closure and the capsule performs the swell —
  `SidebarActionCapsule`, `TopBarActionCapsule`, `NavCluster`,
  `SettingsNavCapsule` are the four that do this.
- **Where a wash would be wrong, answer some other way, but answer.** A colour
  swatch cannot take a white wash — it would be showing the wrong colour — so
  `SpaceSwatchChip` answers the pointer with its ring. A control drawn as a
  recessed well (`Surface.well` is black ink) cannot be lifted with a white
  wash either; `SettingsShortcutRecorder` brightens its ink instead. Both still
  swell.
- **An `NSButton` takes the press around `NSControl`'s tracking loop**, which
  does not return until the mouse comes back up. Set the state either side of
  `super.mouseDown`, and override `highlight(_:)` for the keyboard's route in —
  `TopBarButton` and `SettingsPushButton` are the two, and the pattern is
  documented on the first of them.
- **Add your control to `Tests/Design/ButtonFeedbackTests.swift`.** That file is
  the register of every button in the app and it exists because "every button
  answers a press" was true in prose and false in six places for months. A new
  button that does not swell should fail a test, not wait for somebody to
  notice.

Full rules and the measured numbers: `docs/UI-SPEC.md` §6, and §3.1/§3.4 for
what the two washes mean elsewhere.

**List rows are not buttons.** A row's highlight is one pill that slides between
rows (`RowPillView`, and the list controller that owns it); a row does not swell,
because a full-width plate growing 5 % is the list jumping rather than a control
being pressed.

## Motion, generally

- Nothing exceeds 0.35 s except the two cases `docs/UI-SPEC.md` §6 marks.
- Everything degrades to instant under Reduce Motion. The helpers in
  `Design/Motion.swift` already check it; hand-rolled `CATransaction`s do not.
- Bounds-derived frames must land on the frame that changed them — wrap them in
  `Tokens.Motion.immediately`. A state (a fill, a ring, an ink) cross-fades.

## Build and test

- `make gen` after adding or removing a file — `Luna.xcodeproj` is generated by
  XcodeGen from `project.yml` and is not committed.
- `make build`, `make test`, `make lint`. A direct `xcodebuild` **must** pass
  `-derivedDataPath DerivedData`, or it builds somewhere else entirely.
- `BrowserKit/` imports no AppKit; `Tools/check-no-appkit.sh` enforces it.
- Check every AppKit and WebKit call against the installed SDK headers before
  using it (`xcrun --show-sdk-path`). Several things that read as available are
  not, and several that look identical resolve to the same colour.

## Design tokens

- Colours, lengths and timings come from `Design/` — `Tokens.Surface`,
  `Tokens.Text`, `Tokens.Line`, `Tokens.Metric`, `Tokens.Motion`. Do not write a
  literal where a token exists, and do not add a token without the measurement
  that produced it.
- `Design/TokenCheck*.swift` asserts the invariants between them at launch. If a
  new token has a relationship to an old one, say so there.
